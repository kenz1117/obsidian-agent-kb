## 二、启动性能（用户反馈"插件启动非常慢"）

### 2.1 根因分析（已实测定位，非推测）

`main.ts` 的 `onload()` 中原本是：

```ts
await this.initializeRuntime();
if (this.settings.mcpEnabled) await this.startMcp();   // ← 阻塞插件加载
```

`startMcp()` → `BackgroundMcpService.start()` 每次都无条件执行：

```
launchctl bootout  →  launchctl bootstrap  →  轮询 /health
```

实测数据：

```
launchctl bootout 耗时          5.01 秒
launchctl bootstrap 耗时        0.00 秒
/health 轮询到健康              0.157 秒
```

**5.01 秒这个数字不是巧合**，它精确等于 Node.js 的默认 `keepAliveTimeout`（5000ms）：

```
$ node -e "const http=require('http');const s=http.createServer();console.log(s.keepAliveTimeout)"
5000
```

因果链条（全部经 `lsof` 验证）：

1. MCP 服务基于 `node:http` + `StreamableHTTPServerTransport`。
2. 服务退出时的 SIGTERM 处理器调用 `server.close()`。
3. `server.close()` **不会关闭处于 keep-alive 状态的空闲 socket**，会一直等到 `keepAliveTimeout` 超时。
4. 真实连接的 Agent（MiniMax Code、Obsidian Electron 等）在 `127.0.0.1:27183` 上持有 ESTABLISHED 的 keep-alive 连接 —— `lsof` 实测同时存在 3 条。
5. 于是 SIGTERM → 进程退出被拖住 5 秒。
6. 插件的 `onload()` 恰好 `await` 了这个 `launchctl bootout`，于是 **Obsidian 的插件加载被阻塞 5 秒**。
7. 更糟的是：README 明确写着"后台服务随系统登录自动运行，关闭 Obsidian 不影响其他 Agent 使用知识库"，但插件每次启动都会把这个本来健康运行的服务**杀掉重启**，顺手打断所有 Agent 的活跃连接。

### 2.2 已实施的三层修复

**第一层 —— 服务停止要快**（`src/runtime/mcp-server.ts`）

```ts
server.close(() => resolve());
server.closeIdleConnections?.();                              // 立即释放空闲 keep-alive
setTimeout(() => server.closeAllConnections?.(), 250).unref?.(); // 250ms 后兜底
```

**实测：bootout 由 5.01 秒 → 0.26 秒。**

**第二层 —— 健康且配置一致就不要重启**（`src/runtime/background-service.ts`）

新增 `isCurrentAndHealthy(settings)`：先比对磁盘上的 `service.json` 与当前期望配置（逐字段一致），再探测 `/health`。两者都成立就直接**接管**现有服务，返回。

这不仅省掉 5 秒，还修掉了一个**正确性 bug**：原实现会在每次 Obsidian 启动时无条件重启服务，导致 Agent 连接被反复打断。

**第三层 —— 插件加载绝不等待服务**（`src/main.ts`）

```ts
if (this.settings.mcpEnabled) void this.startMcp();   // 不再 await
```

服务状态改为显式状态机 `stopped | starting | running | error`，通过 `onServiceStateChange()` 事件推送给 UI；设置页与审阅页都能显示"启动中"中间态。

### 2.3 实测验证

```
启动前 service PID: 82006
重启 Obsidian 后:    82006        ← 服务未被重启，被接管复用
Obsidian 窗口就绪:   0.82 秒
```

### 2.4 仍可改进（非阻塞）

- `service-node` 为 116 MB 的完整 Node 运行时，可考虑改为按需下载或用更小的运行时，减少安装包体积。
- `walk()` 每次搜索都全量遍历 Vault（`knowledge.ts:287`），大 Vault 下建议加 mtime 缓存。
- `collectCards()` 在每次 Vault 元数据变化时全量重扫，建议加增量索引。

## 三、视觉与信息架构重做

### 3.1 改造前的问题

- 6 个队列计数被压成一排小药丸标签，在 583px 宽的侧栏里换行错位，数字与文字挤在一起。
- 卡片是一整块纯文本，元数据（状态/置信度/治理分/更新时间）全部以 `label: value` 字符串形式平铺，扫读成本高。
- 操作按钮 4–5 个纯文字按钮横排，没有视觉层级，"晋升正式"虽是 `mod-cta` 但和其余按钮挤在同一行没有分组。
- 标题没有品牌区，页面缺少视觉锚点。
- 设置页用裸 `createEl('h2')` / `createEl('h3')` 分节，绕过 Obsidian 原生 `Setting.setHeading()`，与社区插件惯例不一致。
- 大量硬编码 px（`border-radius:8px`、`padding:10px`）与 `opacity:.72` 灰度文字，未走 Obsidian 主题变量。
- 卡片标题是可点击的 `div` —— **键盘不可达**，违反无障碍基本要求。

### 3.2 改造后

**知识审阅页（首页）**

- **Hero 区**：数据库图标 + 标题 + 实时统计副标题（"共 15 张知识卡，当前队列 15 张"）+ 44×44px 图标按钮（刷新带旋转反馈、设置带 `aria-label`）。
- **状态条**：服务状态点（绿/黄/红三态）+ 已配置 Agent 数 + 最近连接，键盘可聚焦。
- **6 宫格状态卡**（替代药丸标签）：图标 + 计数 + 名称，按队列着色（待审橙、自动蓝、冲突红、正式绿、归档灰、过期黄），当前队列有描边 + 底部色条；`aria-pressed` 暴露选中态。
- **工具条**：搜索框 + 最低分 + 置信度分段控件。
- **卡片**：左侧队列色条、状态/置信度/治理分胶囊标签（按值着色，低分标红）、操作按钮改为图标 + 文字、展开详情用 `<dl>` 键值网格。
- **空状态**：图标 + 标题 + 引导文案，替代原来一行灰色文字。

**设置页**

- **状态 Hero**：运行状态胶囊（绿点 + 文字）+ 插件名 + 说明 + `127.0.0.1:27183` 代码块。
- **5 个原生分区**（`new Setting(containerEl).setName(...).setHeading()`）：Agent 接入 / 接入状态 / 知识审阅 / 知识库目录 / 偏好设置。
- **Agent 卡片列表**：名称 + Agent ID + 状态胶囊（地址已配置=绿 / 需更新=黄 / 读取失败=红）+ 复制按钮。
- **目录预览**：实时拼出四个队列的最终落盘路径。

### 3.3 CSS 工程化改造

`styles.css` 从 44 行扁平规则重写为约 900 行的设计系统：

- **全部颜色走 Obsidian 主题变量**，浅色/深色/社区主题自动适配（已实测深色模式）。
- **4px 间距网格**（`--size-4-*`，带字面量 fallback 兼容旧主题）。
- **所有选择器统一作用域到 `:is(.oakb-review, .oakb-settings, .oakb-modal)`**，既满足官方"scope CSS to plugin container"规则，也解决了下面 3.4 的特异性问题。
- 无 `!important`、无 `:has()`、无内联样式。

### 3.4 过程中实测发现的两个隐蔽 CSS 陷阱

这两个问题**读代码看不出来**，是靠 CDP 读取真实计算样式才定位的：

**陷阱一：Obsidian 的全局 `button` 样式会压过插件样式**

```css
/* Obsidian app.css */
button { height: var(--input-height); padding: var(--size-4-1) var(--size-4-3); }
button:not(.clickable-icon) { background: var(--interactive-normal); }
```

- `button:not(.clickable-icon)` 的特异性是 **(0,1,1)**，而插件里朴素的 `.oakb-card__title` 只有 **(0,1,0)** → 卡片标题渲染出灰色按钮底色。
- `button { height: var(--input-height) }`（固定 30px）让统计磁贴高度被钉死，内容溢出后标签**跑出卡片边框 12px**。
- Chrome 的 `<button>` 还会垂直居中内容，溢出的图标因此被推到卡片**上方**。

**修复**：所有按钮类选择器都加作用域（提升到 (0,2,0)），并显式重置 `height: auto; justify-content: flex-start; appearance: none; background: transparent;`。

**陷阱二：`<button>` 的内容垂直居中**

统计磁贴内图标溢出到边框外，就是 Chrome 对 `<button>` 默认 `align-items:center` 的行为。纯看 CSS 很难联想到，必须量。

### 3.5 第二轮反馈的修复（实测）

用户在真机使用后提了三条反馈，均已修复并实测：

**反馈 1 ——「来源」按钮无用，删除；打开/转正/归档改成标题行右侧的三个小按钮。**

- 移除 `来源` 按钮，并连带删除因此变成孤儿的 `OakbPluginApi.openSource()` 与 `main.ts` 中的实现（避免死代码）。
- 卡片头部改为 `标题 + 三个 32×32 方形图标按钮`，按钮组 `flex-shrink: 0`，标题 `flex: 1 1 auto; min-width: 0`。
- 实测卡片头部子节点：`oakb-card__title` + `oakb-card__quick`。

**反馈 2 —— 切换置信度筛选时搜索框宽度会突变。**

实测数据（修复前）：

| 选中项 | 搜索框宽度 | 分段控件所在行 |
| --- | --- | --- |
| 全部 | 428px | 第 2 行 |
| high | 428px | 第 2 行 |
| medium | 210px | 第 1 行 |
| low | 211px | 第 1 行 |

根因是**两个叠加的尺寸抖动**：

1. 选中态按钮的 `font-weight` 从 400 变成 600 → 分段控件自身宽度变化 → flex 换行判定翻转 → 搜索框（`flex-grow: 1`）吸收全部剩余空间。
2. 筛选后卡片变少 → 列表不再超出视口 → 纵向滚动条消失 → 可用宽度多出约 15px。

修复：

- 分段控件所有按钮统一 `font-weight: 400`，选中态只用背景色与文字色区分 → **控件宽度恒定**。
- `.oakb-search { flex: 1 1 0; min-width: 120px }`、`.oakb-segment { flex-shrink: 0 }`、`.oakb-score { flex-shrink: 0 }`。
- `.oakb-review { scrollbar-gutter: stable }` → **滚动条槽位恒定**，内容宽度不再因筛选结果长短而变。

实测修复后：四种筛选下搜索框宽度**恒为 197px**，分段控件恒在第 1 行。

**反馈 3 —— 标题过长把右侧按钮挤出卡片。**

- 标题改为单行省略（`overflow: hidden; text-overflow: ellipsis; white-space: nowrap`），并同步写入 `title` 属性供悬停查看全文。
- 实测 15 张卡中 6 张标题被正确截断，操作按钮始终在位。

### 3.6 过程中新发现并修复的一个竞态

截图复核时发现状态条出现**三条重复的"最近连接"**。根因是 `renderStatus()` 被两条路径并发触发（Vault 元数据变化 → `refresh()`；服务状态变化 → 事件监听），两次异步渲染各自 `empty()` 后又各自追加。

修复：引入 `statusRenderToken`，每次渲染先把内容构建到脱离文档的 fragment 中，只有当 token 仍是最新时才整体换入。实测恢复为一条。

## 五、非插件层审计（packages/core / mcp / cli / apps/gateway）

> 本节由独立审计通道执行，覆盖插件包以外的全部代码。以下为按严重度排序的结论。

### 5.1 阻塞级

**B1. lockfile 与 package.json 不同步，CI 从未真正跑过测试**

`pnpm-lock.yaml:15-19,43-50` 仍声明 `@oakb/core@workspace:*` 与 MCP SDK `^1.0.0`，但 `packages/cli/package.json`、`packages/mcp/package.json` 已无这些依赖。复现结果：

```
ERR_PNPM_OUTDATED_LOCKFILE  1 dependencies were removed: @oakb/core@workspace:*
```

两个 workflow 都用 `pnpm install --frozen-lockfile`（`ci.yml:22`、`obsidian-plugin.yml:22`）→ 安装步骤即失败 → **node job 根本到不了 typecheck/build/test，插件发布 workflow 也从不打包**。

> **修复**：本地跑一次 `pnpm install --no-frozen-lockfile` 并提交新的 lockfile；同时在 CI 增加"断言 `pnpm install --frozen-lockfile` 成功"的步骤。

**B2. `@oakb/core` 无人使用 —— 仓库里有第三套治理引擎**

全仓检索：没有任何源文件 import `@oakb/core`，只有它自己的测试在用。当前并存三套治理实现：

1. `packages/core/src/governance.ts`（TS）
2. `apps/gateway/src/oakb_gateway/governance.py`（Python）
3. `packages/obsidian-plugin/src/domain.ts`（插件，实际在用的那套）

三套的阈值、评分规则、路由策略各不相同（见 5.2 D3/D4），且三套 frontmatter 解析器对 `tags: [a, b]` 的解析结果都不一样。

> **修复**：要么删除 `packages/core`，要么让它成为唯一实现被插件 + CLI 共用。现状必然导致静默分叉。

### 5.2 高危

**H1. 晋升逻辑信任知识卡自报的 `governance_score`**

`apps/gateway/src/oakb_gateway/governance.py:454` 直接读 frontmatter 里的 `governance_score` 与阈值 80 比较，晋升时不重算分数。frontmatter 是纯文本，任何 Agent 都能改成 `governance_score: 100` 后被 `oakb promote` 提升为正式知识。

> **修复**：晋升时用 `score_card()` / `route_card()` 重算，忽略存储值，并要求显式审阅人身份。

**H2. `packages/core/src/governance.ts:156-163` 死分支：`accept` 永远不可达**

```ts
if (scored.score < policy.quality.min_canonical_score) { decision = 'review'; }
else                                          { decision = 'review'; }   // ← 两边都是 review
```

实测：97 分（≥80）的卡片仍返回 `review`；`types.ts:22` 定义的 `'accept'` 永远不会被返回；`min_review_score` 也从未被读取（`:152-155` 是硬编码 40/60）。

> **修复**：`else` 分支返回 `'accept'`，两个阈值都从 policy 读取。

**H3. Agent 身份靠环境变量自证，可被任意本地进程冒充**

`apps/gateway/src/oakb_gateway/server.py:33` 从环境变量读 `AGENT_ID`，`:136` 只校验是否在 `REGISTERED_IDS` 名单里。任何能 spawn `apps/gateway/bin/oakb-mcp` 的本地进程，只要设 `KB_AGENT_ID=codex`，其写入的知识卡、会话与审计记录都会被记到别的 Agent 名下。

> **注意**：插件自带的 HTTP MCP 路径**没有**这个问题 —— `mcp-server.ts:50,66-67` 把身份绑定在 token 上。建议把插件的做法推广到 Python 网关。

**H4. 密钥扫描闸门形同虚设**

`apps/gateway/bin/oakb-auto-ingest:92-93`：先 `git add -A`，再调用 `oakb-secret-scan "$VAULT"`（**未带 `--staged`**），而扫描器 `bin/oakb-secret-scan:16` 只 diff **未暂存**的变更 → `git add -A` 之后这个 diff 恒为空 → 扫描永远返回 "clean" → 紧接着 `:94-96` 就 commit 并 push。

复现：同一临时仓库，带 `--staged` 返回 `rejected`（exit 2），不带则返回 `{"status":"clean"}`（exit 0）。

更糟的是 `tests/test_secret_scanner.py:11-15` 只断言 `returncode != 0`，在非 git 目录下扫描器直接抛 `CalledProcessError` 崩溃退出 1 —— **测试是因为崩溃才通过的，不是因为检测到了密钥**。

> **修复**：`oakb-auto-ingest` 改传 `--staged`；扫描器改为扫文件（`git ls-files -co --exclude-standard` + 内容正则）而非只扫 diff；测试断言 `json.loads(stderr)["status"] == "rejected"`。

**H5. 审计日志可伪造、可截断、无链式完整性**

`server.py:146-163` 往 `RUNTIME/audit/YYYY/MM/DD.jsonl` 追加纯 JSONL：无哈希链、无签名、无文件锁 → 任何有写权限的进程都能改行或删行。而 `automation.py:287-294` 遇到解析不了的行会**静默跳过**，篡改痕迹不产生任何告警。

更混乱的是 `governance.py:400,484,502` 把晋升/归档事件写到 `APP_ROOT/runtime/governance.jsonl`，**绕过了 `KB_RUNTIME_DIR`** → 治理轨迹落在仓库目录而不是配置的 runtime 目录。

> **修复**：统一到 `RUNTIME` 下的单一 sink，加 `prev_hash` + HMAC 链，记录 `policy_version/score/actor`，审计写失败必须 fail-closed，补一个 `verify` 命令。

## 六、AI 自动判定（决策模型）——新增能力

用户提出"能不能接入决策模型让 AI 自动判断，只把拿不准的转人工"。**已实现**，设计与用法见 [`docs/decision-model.md`](./decision-model.md)。

要点：

- **模型建议**：主选阿里云百炼 `decision-model-preview`（原生返回概率分布与置信度，正是自动/转人工闸门需要的信号）；同时支持任意 OpenAI 兼容模型作为兜底或私有化部署。
- **分级判定**：硬性治理规则 → 模型判定 → 只有"可判定 + 高置信度"的卡片自动处理，其余带理由转人工。
- **模型永远无法绕过硬规则**：`planAutoAction()` 的求值顺序把硬规则放在第一位。这条设计直接对应审计里的 H1（晋升时信任卡片自报的分数）。
- **密钥不进 Vault**：优先读环境变量，其次读 `~/Library/Application Support/obsidian-agent-kb/secrets.json`（`0600`），**绝不写进 `data.json`**——后者会被 Vault 同步或 Git 带走。
- **默认安全姿态**：功能默认关、演练模式默认开、自动晋升/自动归档默认关、置信度阈值 0.85。
- **审计留痕**：每次判定追加一行到 `runtime/decisions.jsonl`；自动晋升还会把置信度、模型名与理由写进 frontmatter。
- **验证**：14 项单元测试 + 用本地 mock 服务在真实 Obsidian 中端到端验证（请求体、鉴权头、弹窗渲染、批量流程、演练模式不落库）。
